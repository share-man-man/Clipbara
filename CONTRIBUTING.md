# Contributing to Clipbara

Thank you for your interest in contributing to Clipbara! This guide will help you get started.

## Prerequisites

- macOS 14 (Sonoma) or later
- Xcode 16.0 or later (the iPhone app needs Xcode 26)
- [xcodegen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`)

## Development Setup

1. Fork and clone the repository:
   ```bash
   git clone https://github.com/<your-username>/Clipbara.git
   cd Clipbara
   ```

2. Set up signing with your own team (optional, but recommended):
   ```bash
   cp Config/Local.xcconfig.example Config/Local.xcconfig
   ```
   Set `DEVELOPMENT_TEAM` to your team ID (Xcode > Settings > Apple Accounts; a free Personal Team works). `Config/Local.xcconfig` is gitignored. Signed with Apple Development, the build keeps its Accessibility permission across rebuilds. Without the file it is signed ad-hoc, and macOS drops the permission whenever the code changes. Add `-allowProvisioningUpdates` to the first command-line build.

3. Generate the Xcode project:
   ```bash
   xcodegen generate
   ```

4. Open in Xcode:
   ```bash
   open Clipbara.xcodeproj
   ```

5. Build and run with `Cmd + R`.

> **Note:** The `.xcodeproj` is generated by xcodegen and is not tracked in git. Always run `xcodegen generate` after cloning or pulling changes to `project.yml`.

## Build Variants

Each configuration has its own bundle ID, so the builds keep their data, settings and permissions apart and can run side by side.

| Configuration | App | Bundle ID | URL scheme | Notes |
| --- | --- | --- | --- | --- |
| Debug | `ClipbaraDev` | `com.minsang.PasteClip.dev` | `clipbara-dev` | `AppIcon-Dev` icon, DEV badge and banner, no Sparkle |
| Local | `ClipbaraLocal` | `com.minsang.PasteClip.local` | `clipbara-local` | Release-optimized, for everyday use, no self-update |
| Release | `Clipbara` | `com.minsang.PasteClip` | `clipbara` | The shipped build, updated by Sparkle |

Build and relaunch the Debug app from the command line:

```bash
xcodebuild -project Clipbara.xcodeproj -scheme Clipbara -configuration Debug build
pkill -f ClipbaraDev.app || true
open ~/Library/Developer/Xcode/DerivedData/Clipbara-*/Build/Products/Debug/ClipbaraDev.app
```

Use `pkill -f ClipbaraDev.app`, not `Clipbara.app`, which also quits an installed release.

`bash scripts/install-local.sh` builds the Local configuration, installs it to `/Applications/ClipbaraLocal.app` and relaunches it. It is sandboxed, so its data lives in its own container. The `CLIPBARA_NO_SELF_UPDATE` compilation condition turns Sparkle off; with it on, Sparkle would replace the app with the upstream release.

The build settings `CLIPBARA_BUILD_BADGE` (a badge next to the menu bar icon) and `CLIPBARA_BUILD_BANNER` (the orange header at the top of the menu) reach Info.plist as `ClipbaraBuildBadge` and `ClipbaraBuildBanner`, which `Bundle+BuildInfo.swift` reads. Empty means not shown. Don't check in code whether this is a development build; set these per configuration in `project.yml` instead. If you change `AppIcon`, regenerate `AppIcon-Dev` with `bash scripts/make-dev-icon.sh`.

## Architecture

The project follows a clean separation of concerns:

```
Clipbara/
├── Models/          # SwiftData models (ClipboardItem)
├── Services/        # Core logic (ClipboardMonitor, PasteService, etc.)
├── Panel/           # NSPanel + NSHostingView hosting layer
├── Views/           # SwiftUI views
├── Utilities/       # Helpers and extensions
└── Resources/       # Assets, Info.plist, entitlements
```

## Key Patterns

### Swift 6 Strict Concurrency
This project uses `SWIFT_STRICT_CONCURRENCY: complete`. All UI-related code must be annotated with `@MainActor`. Use `@Observable` for observable classes.

### Marking Clipbara's Own Pasteboard Writes
Anything Clipbara writes to the pasteboard must carry the `OwnPasteboardWrite.mark` (or `OwnPasteboardWrite.type`) marker. The clipboard monitor ignores marked changes, so it does not re-capture what was just pasted. This replaces the old `skipNextChange()` flag, which swallowed copies made in quick succession.

### NSPanel + NSHostingView
The clipboard panel uses a non-activating `NSPanel` to avoid stealing focus from the frontmost app. SwiftUI views are hosted via `NSHostingView`.

### SwiftData
- Call `try? modelContext.save()` after every insert, delete or update. Don't rely on autosave.
- Don't use `#Index` or `#Unique`: they need macOS 15, and the app targets macOS 14.
- Inside an `NSHostingView`, don't show a view that has a `@Query` through `if`/`else`. Destroying and recreating it can break `@Query` syncing. Keep it in a `ZStack` and switch its `opacity` instead.

## Code Style

- Follow existing code conventions in the project
- Use Swift 6 concurrency features (`async/await`, `@Sendable`)
- Prefer value types (`struct`, `enum`) over reference types where appropriate
- Use SwiftData's `@Model` for data modeling (see the SwiftData notes above)

## Pull Request Process

1. Create a feature branch from `main`:
   ```bash
   git checkout -b feature/your-feature-name
   ```

2. Make your changes and test thoroughly.

3. Ensure the project builds without warnings:
   ```bash
   xcodegen generate
   xcodebuild -project Clipbara.xcodeproj -scheme Clipbara -configuration Debug build
   ```

4. Push your branch and open a Pull Request.

5. Fill out the PR template with a clear description of your changes.

## Releases

Releases are made by the maintainer. The steps are in [docs/releasing.md](docs/releasing.md).

## Issue Guidelines

- **Bug reports**: Use the bug report template. Include your macOS version, app version, and steps to reproduce.
- **Feature requests**: Use the feature request template. Describe the problem you're trying to solve.
- **Questions**: Open a discussion or issue with the question label.

Before opening a new issue, please search existing issues to avoid duplicates.
